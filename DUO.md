# Design URnetwork for windows, not devices

URnetwork should optimize for foldables by first deleting the code that asks what device each app runs on, then spending the saved effort on a layout that puts locations beside the connect button, which none of the surveyed VPN clients ship. Both apps choose layouts by device type: Android through an `isTablet()` test of screen diagonal and orientation, and Apple through `userInterfaceIdiom == .pad` checks and an iPhone portrait lock keyed to the idiom. Apple (the idiom is "no longer meaningful for any kind of layout decision") and Google (size classes "are not intended for isTablet-type logic") now tell developers to stop doing exactly this. **Android is the urgent case:** the app declares no `configChanges` and holds 214 pieces of UI state in plain `remember` against 9 in `rememberSaveable`. Every unfold therefore closes open sheets, clears typed text, collapses the connect drawer and can abort an F-Droid checkout mid-payment, which fails Google's baseline Tier 3 continuity test. **The Apple app is closer than it looks**, because its connect drawer and column limits already follow size class and window width. On the new iPhone Duo, though, its iPad layouts never appear and its portrait lock does nothing. The Duo counts as a phone (the phone idiom), yet its 7.6-inch inner display reports the same regular width and height size classes as an iPad. **The binding deadline is Apple's: from April 2027, every App Store submission must include iPhone Duo screenshots.** Google Play's August 2027 move to API 37 changes little for an app that already declares no orientation locks. By December, the plan makes both apps survive the fold: state continuity, size-class navigation, and a connect screen that fits short windows. Before April, it brings the Mac app's existing layout, with the provider table beside the connect button, to iPad, the Duo's inner display, and Android windows of medium width and up. Device priorities follow Samsung's Fold7 and Fold8 family and the iPhone Duo. Flip phones are a small-window case served mainly by the Quick Settings tile, the notification and widgets. Huawei's HarmonyOS foldables and tri-folds need only emulator checks.

## Apple and Google now treat every fold as a window resize

Apple shipped its first foldable on **23 October 2026**. The **iPhone Duo**, announced 9 September, pairs a **7.6-inch inner display with a 5.4-inch outer display of the same aspect ratio**, starts at $1,999 and runs iOS 27.1 ([Apple Newsroom](https://www.apple.com/newsroom/2026/09/apple-unveils-iphone-duo/)). How Apple tells developers to treat it matters more than the hardware. Apps stay iPhone apps in the phone idiom, and opening or closing the device resizes the running app rather than relaunching it: "Your app may react to different size class boundaries, but it is still an iPhone app" ([Tech Talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/)). The outer display reports ordinary iPhone size classes: compact width, with regular height in portrait. The inner display reports **regular width and regular height, the same size classes as an iPad, given to an app that still has the phone idiom, and it "doesn't honor your supported interface orientations"** ([Tech Talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/)).

The fold is a separate input, not a size-class change. iOS 27.1 reports it as a reserved "division" region, active only when the device is partly folded and zero-width when flat. It adds `ArrangementView`, which lays out a primary and a secondary view around that region. It also adds `onHingeChange`, which Apple recommends for interactions and effects rather than layout: "For layout, use the arrangement and region APIs" ([Tech Talk 111463](https://developer.apple.com/videos/play/tech-talks/111463/); [Tech Talk 111464](https://developer.apple.com/videos/play/tech-talks/111464/)).

The SDK an app is built with decides what Duo owners see. Apps built with older SDKs run at "a familiar size and aspect ratio" on the inner display. **Apps built with the iOS 27.1 SDK fill the screen edge to edge, and their standard navigation and toolbar buttons move into vertical bars along the side** ([Tech Talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/)). Only bars supplied by system containers make that move: a SwiftUI `.toolbar` on a `NavigationStack` or `NavigationSplitView`, or a system tab bar. Because "controls sit along one edge," the safe area is uneven, and custom bars and custom drawers must handle that themselves ([Preparing your app for iPhone Duo](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo); [HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)). The Duo also brings Split View to the iPhone. On the inner display only, it allows several windows of the same app, for any app that already supports multiple scenes on iPad ([Tech Talk 111464](https://developer.apple.com/videos/play/tech-talks/111464/)). Apple's own Safari reportedly launched with a "cramped layout" on the Duo ([MacRumors](https://www.macrumors.com/roundup/iphone-duo/)), so the device catches phone-only assumptions even in Apple's own apps.

The Duo completes a two-year push. At WWDC25 Apple deprecated `UIRequiresFullScreen` and stopped scaling or letterboxing iOS 26 SDK apps on new screen sizes ([WWDC25 session 282](https://developer.apple.com/videos/play/wwdc2025/282/)). At WWDC26 Apple made the scene lifecycle mandatory for apps built with the latest SDK. It made iPhone-only apps freely resizable on iPad and in iPhone Mirroring on the Mac, where they "will always be running in the portrait interface orientation, regardless of the aspect ratio." It also called the idiom "no longer meaningful for any kind of layout decision," and reduced supported orientations to "a preference… ignored when your app is running in a resizable environment" ([WWDC26 session 278](https://developer.apple.com/videos/play/wwdc2026/278/)). One contradiction is unresolved. The same Duo talk that says the inner display ignores supported orientations also says the Duo "respects your supported interface orientations, but your app will scale on the inner display" ([Tech Talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/)). Either way, a portrait-only iPhone app gets a lock that is ignored or a scaled compatibility view on the inner display. URnetwork wants neither.

Android's version of these rules arrived earlier and already applies. For apps targeting **API 36**, the system ignores orientation, resizability and aspect-ratio restrictions on any display whose smallest width is at least 600dp, and the app fills the window without letterboxing ([Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)). Google Play has required API 36 for new apps and updates since **31 August 2026**, with extensions to 1 November ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/11926878)). Google says Play will require **API 37 in August 2027**, which removes the temporary opt-out ([Android Developers Blog](https://developer.android.com/blog/posts/prepare-your-app-for-the-resizability-and-orientation-changes-in-android-17)).

**The two platforms differ on one point, and it sets URnetwork's priorities.** On iOS, a fold resizes a living scene, so view state survives by default. On Android, folding or unfolding is a configuration change that destroys and recreates the activity, which "clears out any state kept as fields in the Activity." Google prescribes ViewModels for in-memory state and `rememberSaveable` for transient UI state. It recommends that Compose-only apps handle size changes directly, but warns that this does not replace saving state, because "it is impossible to entirely disable Activity recreation" ([Handle configuration changes](https://developer.android.com/guide/topics/resources/runtime-changes)). Android 17 raises the cost: after a configuration change the app doesn't handle itself, the system no longer restores the keyboard ([Android 17 behavior changes](https://developer.android.com/about/versions/17/behavior-changes-all)).

Google enforces quality through ratings and badges rather than rejection. Its adaptive app quality guidelines make **Tier 3, "Adaptive ready," the floor**. Tier 3 means no letterboxing and full function in multi-window. Its `Config_Changes` item requires apps to keep state "when the device rotates, the window resizes, or the device folds or unfolds" ([Tier 3](https://developer.android.com/guide/topics/large-screens/tier-3-overview)). Meeting Tier 2 at every screen size, or Tier 1, qualifies an app for the **"Optimized for large screens"** Play badge ([Adaptive app quality guidelines](https://developer.android.com/docs/quality-guidelines/large-screen-app-quality); [Android Developers Blog](https://android-developers.googleblog.com/2026/05/android-adaptive-development-ecosystem.html)). Since 2022, Play has also shown separate ratings by device type, so a weak foldable experience appears as its own score in front of people shopping on foldables ([Android Developers Blog](https://android-developers.googleblog.com/2022/03/helping-users-discover-quality-apps-on.html)).

The libraries moved as well. Compose Material 3 Adaptive 1.3.0, stable since 12 August 2026, deprecates `currentWindowAdaptiveInfo()` in favor of `currentWindowAdaptiveInfoV2()`. The new version adds large (1200dp and up) and extra-large (1600dp and up) width classes ([Material 3 Adaptive release notes](https://developer.android.com/jetpack/androidx/releases/compose-material3-adaptive)). The stock `NavigationSuiteScaffold` already shows a bottom bar when width or height is compact or the device is in tabletop posture, and a side rail everywhere else ([Build adaptive navigation](https://developer.android.com/develop/adaptive-apps/guides/build-adaptive-navigation)).

## Samsung's Fold line and iPhone Duo set the screens that matter

By volume, foldables are still a niche: about **2.5% of smartphone shipments** in Q3 2025 ([Counterpoint](https://www.counterpointresearch.com/insights/global-foldable-smartphone-market-q3-2025/)). Forecasts for 2026 cluster around **22–27 million units** ([SAG](https://smartanalyticsglobal.com/global-foldable-smartphone-market-q2-2026/); [Omdia via SammyFans](https://www.sammyfans.com/2026/08/20/foldable-smartphone-shipments-set-to-more-than-double-by-2028/)). Market trackers disagree on shares; their estimates of Huawei's H1 2026 share range from 40% to 57%. They agree on the structure that matters. Most of Huawei's lead is in China, on HarmonyOS NEXT, which cannot install Android apps ([PhoneArena](https://www.phonearena.com/news/huawei-phones-outside-china-can-run-android-apps_id152936)). Outside China, Samsung dominates Android foldables, with about **64% of global foldable shipments** in Q3 2025 ([Notebookcheck](https://www.notebookcheck.net/Samsung-regains-a-dominant-64-share-of-the-global-foldable-market-as-shipments-rise-14.1177215.0.html)).

Counterpoint forecasts Apple at **25% of 2026 foldable units** after a single quarter on sale, and **40% in 2027** ([Counterpoint](https://counterpointresearch.com/en/insights/global-foldable-shipments-to-hit-100-million-cumulative-milestone-by-end-of-2026)). SAG expects Apple to become the largest foldable vendor in 2027 ([SAG](https://smartanalyticsglobal.com/global-foldable-smartphone-market-q2-2026/)). That would make the Duo the best-selling foldable line within a year. For now, pre-order deliveries have slipped into January 2027, so few developers will have one before then ([MacRumors](https://www.macrumors.com/roundup/iphone-duo/)).

Who buys foldables matters more than how many ship. Google's internal data says people who use more than one device spend 9 times more than phone-only users, and up to 14 times more on foldables ([Android Developers Blog](https://android-developers.googleblog.com/2026/05/android-adaptive-development-ecosystem.html)). That describes who buys foldables; it doesn't forecast what optimizing will earn. One concrete data point: an earlier Google case study found that optimizing its Duo video-calling app (unrelated to the iPhone) for large screens raised its average rating on optimized tablets by about half a point ([Android Developers](https://developer.android.com/stories/apps/google-duo)).

The device mix is shifting toward wide book-style foldables. Book-style models overtook flip phones in 2025, 52% to 48%, and are forecast at about 65% of 2026 shipments ([Counterpoint](https://counterpointresearch.com/de/insights/Book-Type-Devices-to-Reach-of-Global-Foldable-Smartphone-Shipments-in-2026)). Flip-phone panel shipments fell 62% in H1 2026 ([Channel Insider](https://www.channelinsider.com/channel-business/news-book-style-foldable-display-market-growth/)). Samsung's **Galaxy Z Fold8** introduced a 7.6-inch 4:3 inner display (2448×1848), sold alongside the near-square 8-inch Fold8 Ultra ([GSMArena](https://www.gsmarena.com/samsung_galaxy_z_fold8_goes_wide_fold8_ultra_aims_for_the_foldable_crown-news-73825.php)). Google warns that the Fold8 has "a landscape-first natural orientation," so code that assumes rotation zero means portrait breaks ([Android Developers Blog](https://android-developers.googleblog.com/2026/07/optimize-galaxy-screen-sizes.html)). Omdia expects wide panels to make up more than 60% of foldable panels in 2027 ([Omdia via Cyprus Mail](https://cyprus-mail.com/2026/10/26/samsung-and-apple-fuel-rebound-in-foldable-display-shipments)). Layout code now has to handle four screen shapes: tall flip-phone main screens, small near-square flip-phone cover screens, near-square inner screens on book-style foldables, and wide inner screens on book-style foldables such as the Fold8's and the Duo's.

The table below estimates the window each 2026 screen gives an app and how URnetwork behaves there today. Manufacturers publish neither default densities nor sizes in dp. The Android figures are therefore my estimates at a 420dpi reference density. Real default densities or user zoom can shift them by 15–20%. Apple has not published Duo point sizes. The near-square inner screens sit right at Google's 840dp line between the Medium and Expanded width classes, which is where hard-coded thresholds misbehave ([Use window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)).

That table sets the priorities. Samsung's Fold7, Fold8 and Fold8 Ultra inner screens, plus both Duo displays, come first. The Pixel 10/11 Pro Fold and Motorola's new Razr Fold come second. Their inner screens are near-square, like those of the Fold7 and Fold8 Ultra. The Pixel's inner screen, roughly 791×820dp, is the device most likely to break a layout switch hard-coded at 840dp. Flip phones need no separate design; their cover screens are just another small window. Samsung's Flip8 cover runs twelve Samsung apps and four third-party "Labs" apps, and anything else requires the Good Lock MultiStar module ([Android Authority](https://www.androidauthority.com/galaxy-z-flip-8-cover-screen-apps-3688143/)). Motorola, by contrast, lets users put nearly any app on the Razr's cover, which is roughly 400dp square ([Android Central](https://androidcentral.com/apps-software/how-set-up-use-motorola-razr-cover-screen-apps)). Tri-folds need only an emulator pass, not design work: Samsung's Galaxy Z TriFold is "a limited-volume pilot" ([Counterpoint](https://www.counterpointresearch.com/insights/global-foldable-smartphone-market-q3-2025/)), and Huawei's tri-folds run HarmonyOS.

Small windows are no longer only a flip-phone problem. Android 17's App Bubbles let users float any app in a small window on ordinary phones and foldables ([Android 17 is here](https://android-developers.googleblog.com/2026/06/Android-17.html)), so windows that are compact in both dimensions are now common. The same layout code also serves split-screen halves, desktop-style windows and external displays. A foldable iPad or Mac is still a rumor, most often dated to 2028 ([Tom's Guide](https://www.tomsguide.com/computing/ipads/apples-giant-foldable-ipad-likely-wont-launch-until-2028-what-weve-heard)). The macOS target needs no foldable work beyond compiling the shared views.

## No surveyed VPN puts locations beside connect, but URnetwork's Mac app does

VPN apps do little with large screens, so URnetwork can get ahead here instead of catching up. Among the open-source Android clients whose code was read, **Mullvad** is the most adaptive. It unlocked every orientation in 2024 after warning that rotation was "more work than just updating the manifest due to how configuration changes are handled." In April 2026 it added a 40/60 list-detail layout for settings on windows wider than 600dp, and in August 2026 it made its globe interactive ([Mullvad issue #3395](https://github.com/mullvad/mullvadvpn-app/issues/3395); [Mullvad changelog](https://github.com/mullvad/mullvadvpn-app/blob/main/android/CHANGELOG.md)). **Proton VPN** centers content in an 800dp column ([Dimensions.kt](https://github.com/ProtonVPN/android-app/blob/master/app/src/main/java/com/protonvpn/android/base/ui/Dimensions.kt)) and has had an open "sign-in issues in small height situation" bug since 2022 ([Proton issue #87](https://github.com/ProtonVPN/android-app/issues/87)). **PIA** centers a 520dp column ([ConnectionScreen.kt](https://github.com/pia-foss/mobile-android/blob/HEAD/features/connection/src/main/java/com/kape/connection/ui/mobile/ConnectionScreen.kt)), and **Tailscale** avoids recreating its activity by declaring `configChanges` ([Tailscale manifest](https://github.com/tailscale/tailscale-android/blob/main/android/src/main/AndroidManifest.xml)). None of them puts the location list beside the connect button or map. The research found no evidence that the closed-source NordVPN, ExpressVPN, Surfshark or Cloudflare WARP apps do either, and found no VPN with a cover-screen widget.

URnetwork has already built the missing layout once. Its macOS connect view puts the connect button and a 260-point provider table side by side in an `HStack`, with a "Show Provider List" toggle (`sw/Main/Connect/ConnectView-macOS.swift:113-231, 431-443`).

**The pattern to copy is Google's supporting pane.** The connect button, status and globe form the main pane, and the location list is the supporting pane. Google splits them **50/50 at medium width and 70/30 at expanded**. At compact width, the supporting content moves into a sheet or a separate screen ([Canonical layouts](https://developer.android.com/develop/ui/compose/layouts/adaptive/canonical-layouts)). Samsung asks for 50/50 on foldables specifically ([Samsung One UI](https://developer.samsung.com/OneUI/foldable-and-largescreen/intro.html)).

Compose's default pane settings show only one pane at medium width. That is exactly where unfolded book-style phones land in portrait, so URnetwork should opt in with `calculatePaneScaffoldDirectiveWithTwoPanesOnMediumWidth`. Its default `HingePolicy.AvoidSeparating` keeps panes off the fold when the fold splits the screen ([PaneScaffoldDirective.kt](https://github.com/androidx/androidx/blob/androidx-main/compose/material3/adaptive/adaptive-layout/src/commonMain/kotlin/androidx/compose/material3/adaptive/layout/PaneScaffoldDirective.kt)).

On Apple, `ArrangementView` does the same job. Its split style places two views side by side when the container is wider than tall, and stacks them when it is taller. Its overlay style puts the primary view in the bottom part of a half-folded display and the secondary view in the top ([SwiftUI Layout fundamentals](https://developer.apple.com/documentation/swiftui/layout-fundamentals); [Preparing your app for iPhone Duo](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo)). `ArrangementView` is new in the iOS 27.1 SDK, and every Duo ships with iOS 27.1. URnetwork's iOS 16 deployment target only means an availability check, plus a fallback for iPads on older iOS versions.

Apple's guidance cuts both ways: "Don't reinvent your app when it resizes," and "favor small adjustments over rearrangement" ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)). Putting two screens the phone already has side by side satisfies that rule: the connect screen, and the picker that today covers it as a sheet. A separate tablet design would not. There is also a physical argument. A single centered column puts URnetwork's 256-unit connect graphic on the crease of an unfolded book-style device, and Samsung asks apps to keep interactive elements off the crease ([Samsung: Designing for foldable](https://developer.samsung.com/one-ui/largescreen-and-foldable/designing_for_foldable.html)). Two panes move the graphic to the middle of one half.

Navigation should follow size classes and use stock components. On Android, that means the default `NavigationSuiteScaffold` behavior. Samsung backs this up by recommending a side rail for Z Fold devices in portrait ([Samsung One UI](https://developer.samsung.com/OneUI/foldable-and-largescreen/intro.html)). On Apple, it means keeping the system `TabView` and letting iOS 27.1 move it to the side on the Duo. Apple's guidance is "in general, don't override the default bar placement." Toolbar items need both an icon and a title, because vertical bars show icons only. Navigation containers go outside an `ArrangementView`, never inside it ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo); [Preparing your app for iPhone Duo](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo)). Settings and account screens can keep URnetwork's existing centered reading column. Proton's 800dp column shows that this is an acceptable baseline for list screens, and Mullvad's settings list-detail layout is optional polish.

**The connect screen is the one view that has to work in every window, including the short ones:** a landscape phone, a split-screen half, a Razr cover, an Android 17 bubble, a compact iPad window, an iPhone Mirroring window and the Duo's outer display. Google's fix list for the Android 17 change is to cap widths, and to make containers that don't scroll scrollable so that buttons at the bottom stay reachable ([Android Developers Blog](https://developer.android.com/blog/posts/prepare-your-app-for-the-resizability-and-orientation-changes-in-android-17)). Proton's long-open bug about sign-in in short windows shows what happens otherwise.

Keeping state across a fold is easier for a VPN than for most apps. The tunnel runs in the VPN service or network extension, not the activity, so a fold never drops the connection. What a fold destroys is UI state: the open sheet, the search text, a half-finished sign-in. Samsung's checklist asks apps to keep "scroll position" and "text input and the keyboard" across screen switches ([Samsung: Designing for foldable](https://developer.samsung.com/one-ui/largescreen-and-foldable/designing_for_foldable.html)). Apple asks apps to "keep functionality and the state of elements the same between displays" ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)). In SwiftUI the scene survives the fold. But a size-class `if/else` that swaps between different views resets their `@State`, so selection and presentation state belong above the layout switch.

The globe needs the same care. Store the selected location rather than the raw rotation in saved state, and re-fit the view after each resize. Skip expensive re-rendering while a window is being dragged. Apple calls that re-rendering "unnecessary" and signals drags through `onInteractiveResizeChange` ([WWDC25 session 282](https://developer.apple.com/videos/play/wwdc2025/282/); [onInteractiveResizeChange](https://developer.apple.com/documentation/swiftui/view/oninteractiveresizechange(_:))).

**Tabletop posture is a weak case for a VPN.** Google and Samsung frame it around video, camera and calls, with content on the raised half and controls on the flat half ([Foldables quality guidelines](https://developer.android.com/develop/adaptive-apps/quality-guidelines/adaptive-app-quality/experiences/foldables); [Samsung Flex mode](https://developer.samsung.com/one-ui/foldable-and-largescreen/foldable-excl-flex.html)). The research found no VPN or status app with a tabletop layout. Someone in tabletop posture is usually watching video while the VPN runs out of sight. The obligation is defensive: keep drawers, sheets and dialogs off the fold. A full layout with status above the fold and controls below becomes cheap once the two-pane layouts exist, and Apple's overlay arrangement already places the primary view below the fold.

**Flip covers are better served by system surfaces than by layouts.** Samsung's FlexWindow cover screen accepts third-party widgets declared with a `sub_screen` provider, at least 352×339dp and in the keyguard category, and it shows ongoing notifications ([Samsung Flex Window](https://developer.samsung.com/galaxy-z/flex_window.html)). The Quick Settings tile is the VPN's natural control on the cover screen, and Mullvad's changelog works as a checklist for it: label the tile with the action, show the state in the subtitle, prompt to unlock when the phone is locked and open the app on long-press ([Mullvad changelog](https://github.com/mullvad/mullvadvpn-app/blob/main/android/CHANGELOG.md)). The "connected" notification should stay a standard ongoing notification. It fails Android's Live Update criteria, which require a distinct end and exclude "quick access to app features" ([Live Update](https://developer.android.com/develop/ui/views/notifications/live-update)). One tunnel means one UI. URnetwork should not declare support for multiple app instances on Android, and should make iOS multi-window a deliberate choice rather than an Xcode-generated default.

## Three habits explain nearly every gap in both codebases

The codebase audit read both repositories at today's `main` (`android` at `53be1043d`, `apple` at `da60f230`). Paths below use the audit's prefixes, all under `~/urnetwork/`: `kt/` is `android/app/app/src/main/java/com/bringyour/network/`, `and/` is `android/app/`, `sw/` is `apple/app/network/` and `ios/` is `apple/app/`. In Android flavor paths, `…` stands for `java/com/bringyour/network`.

**The first habit is choosing layouts by device type and orientation.** On Android, `isTablet()` (`kt/utils/DeviceUtils.kt:9-34`) treats a window as a tablet only if its diagonal is at least 1440dp, or if it is in landscape with a smallest width of at least 600dp. At default density, typical book-style inner displays measure well under 1440dp diagonally. They therefore count as "tablets" only in landscape. That function picks the navigation layout (`kt/ui/MainNavHost.kt:305-313`). Just above it, the app's only adaptive API call, `currentWindowAdaptiveInfo()` at `:296`, runs and its result is never read. A second, width-only function, `isTabletWidth()` (`kt/ui/components/TabletLayout.kt:52-53`), drives 57 call sites that cap column width. It disagrees with `isTablet()` between 600 and 840dp.

On Apple, `TabletLayout.isTablet` is `userInterfaceIdiom == .pad` (`sw/Shared/Extensions/TabletLayout.swift:71-77`). The first-run sign-in screen picks its column layout from the idiom plus `UIDevice.current.orientation` (`sw/Authenticate/LoginInitial/LoginInitialView.swift:56-104, 242-258`). As a result, a narrow window on a landscape iPad gets two half-width columns, and a landscape iPad can launch in one column. The iPhone is locked to portrait twice: once in build settings (`ios/app.xcodeproj/project.pbxproj:1777, 1856`) and once in an app-delegate method that checks the idiom (`sw/AppDelegate.swift:29-35`).

**The second habit is keeping state where recreation destroys it.** The Android app declares no `configChanges` on any of its three activities (`and/app/src/main/AndroidManifest.xml:113-176`). It keeps **214** `remember { mutable… }` values against **9** `rememberSaveable`; I re-checked both counts for this report. Every fold therefore closes open sheets and dialogs (`kt/ui/MainNavHost.kt:620, 666, 710`; `kt/ui/settings/SettingsScreen.kt:204-238`), clears typed text in 19 fields and collapses the connect drawer (`kt/ui/connect/ConnectDrawerState.kt:111-112`). It also closes the F-Droid flavor's web checkout mid-payment, because its `WebView` dialog hangs off a plain `remember` (`and/app/src/webPay/…/ui/upgrade/PlanPurchasers.kt:56, 148-166`). `LoginActivity` re-reads `intent.data` every time it is created, so a fold during an `ur://…?auth_code=` hand-off runs the auth-code login a second time (`and/app/src/google/…/LoginActivity.kt:119-184, 289-299`). These are direct failures of Tier 3's `Config_Changes` item.

The Apple app does better, because its view tree rarely switches layouts based on size. The exception is the sign-in layouts: crossing the switch rebuilds `LoginInitialFormView` and resets its `presentNetworkServerSheet` flag. Apple's real exposure is multi-window. The scene manifest Xcode generates sets `UIApplicationSupportsMultipleScenes = true`. Every view model is shared across the whole app. Two sign-in presenters use `connectedScenes.first` (`sw/Shared/Utilities/ViewControllerUtils.swift:14-20`; `sw/Main/Account/Settings/AddAuthSheet.swift:715-717`). On the Duo's inner display, as on iPad, sign-in can therefore appear in the wrong window.

**The third habit is fixed geometry.** On Android, the connect button is a fixed 256dp square. The drawer below it starts with at least 248dp showing (`kt/ui/connect/ConnectButton.kt:111-116`; `and/app/src/main/res/values/dimens.xml:5`) and always expands to two thirds of the window height (`kt/ui/connect/ConnectScreen.kt:532-535`). On iOS, there is a 256-point canvas, a 112-point spacer and, at compact width only, a fixed 680-point drawer (`sw/Main/Connect/ConnectView-iOS.swift:82, 192`). Yet at regular width, the same file already caps the drawer at the window height. Android's overlays are 512dp cards that don't scroll (`kt/ui/components/overlays/OverlayContent.kt:29-42`), and four iOS sheets have fixed heights between 216 and 320 points.

The design system turns all three habits into rules. `mmm/DESIGNSTYLE.md` lists only phone, tablet and tablet mini as form factors (`:103-125`). It forbids "a separate tablet screen for a width change alone" (`:87-88`) and fixes the drawer at 680pt (`:91-95`). Neither test suite checks window size, posture or recreation. Android runs on a single emulator image, and Apple's harness creates only iPhone simulators (`apple/test-hardware-startup-lib.sh:44-46, 131-159`).

The foundations are better than the gaps suggest. The Android app targets API 36 and declares no restrictions, so it is fully resizable and never letterboxed. The Material 3 adaptive and WindowManager libraries are already on its classpath (`and/app/build.gradle:629-631`). Its ViewModels, back stack and list scroll positions already survive recreation, and its three Glance widgets already choose their layout from their actual size. The Apple app's SwiftUI lifecycle already meets the iOS 27 scene requirement, and it never uses `UIScreen.main` or `UIRequiresFullScreen`. Its connect drawer already floats at regular width (`sw/Main/Connect/ConnectView-iOS.swift:22, 151`), and its column limits are based on width. On the Duo's inner display it therefore starts from a usable single-pane layout, and the Mac target already shows the two-pane layout works.

## A three-phase plan clears the April and August 2027 deadlines

The plan ranks work by how much harm it prevents on common fold events, how many users it reaches and what it costs, and it is timed against the two dated deadlines. **Phase 1, now through December 2026, fixes what breaks.** Its items are small (a manifest attribute, a navigation default, a handful of checks), and they unblock everything after them. **Phase 2, January through March 2027, uses the unfolded space.** It lands before Apple's April 2027 screenshot rule, so the Duo screenshots show a two-pane layout rather than a stretched phone layout. **Phase 3, April through August 2027, is polish and differentiation** ahead of Play's API 37 requirement.

Two items carry most of Phase 1's value. **Item 1** is the attribute `android:configChanges="screenSize|smallestScreenSize|screenLayout|orientation|density"`. Google recommends handling size changes this way for Compose-only apps. Tailscale ships it, and Samsung's developer blog recommends it ([Samsung Developers blog](https://developer.samsung.com/sdp/blog/en/2024/01/09/best-practices-of-app-development-for-various-screen-sizespowered-by-good-lock)). This one change removes the fold-triggered losses described above, including the keyboard dismissal that Android 17 introduces. The `density` flag covers inner and cover displays with different pixel densities; Google's tri-fold guidance names density restarts as a cause of data loss ([Trifolds and landscape foldables](https://developer.android.com/develop/adaptive-apps/guides/foldables/trifolds-and-landscape-foldables)). Item 1 cannot stand alone, because process death and other configuration changes still recreate the activity. That is why item 2 saves state anyway.

**On Apple, item 5's drawer fix is one line in practice:** apply the regular-width height cap at compact width too. It matters because the Duo's outer display is unusually short for an iPhone. Suppose it renders at 3× like other 460-ppi iPhones. That is an assumption, since Apple has not published point sizes. The portrait window would then be about 466×678 points, shorter than the fixed 680-point drawer. **Item 6 should come early**, because the Xcode 27.1 build changes the layout under test. It adds side bars and edge-to-edge content.

Testing should rely on tools that exist today rather than on hardware that is hard to get. On Apple, those tools are Xcode 27.1's Duo simulator, which opens, closes, rotates and folds the device and supports Split View; Xcode 27's preview resize mode; iPhone Mirroring on macOS 27 for free-form resizing; and Xcode 27.1's App Resizability agent skill, which flags idiom and orientation checks ([Tech Talk 111461](https://developer.apple.com/videos/play/tech-talks/111461/); [WWDC26 session 278](https://developer.apple.com/videos/play/wwdc2026/278/)). On Android, Google's reference test configurations include an 841×701dp foldable. Its tooling covers state restoration (`StateRestorationTester`), forced window sizes (`DeviceConfigurationOverride`) and real posture changes on emulators (Espresso Device's `setTabletopMode`) ([Testing tools](https://developer.android.com/training/testing/different-screens/tools); [Adaptive app quality guidelines](https://developer.android.com/docs/quality-guidelines/large-screen-app-quality)). New test automation should not be built on Firebase Test Lab, which shuts down on 30 September 2027.

The plan deliberately leaves out rear-display and dual-screen modes, which suit camera and translation apps ([Support foldable display modes](https://developer.android.com/develop/adaptive-apps/guides/foldables/support-foldable-display-modes)). It also leaves out multiple Android instances, drag and drop, and any HarmonyOS build.

## Conclusion

On Apple's side, the iPhone Duo changed what "foldable support" means. It is not a special mode with special APIs. It is the general resizing problem Apple has pushed since WWDC25, so a universal SwiftUI app that already picks layouts by size class gets most of the Duo for free. For URnetwork, only a handful of idiom checks and a portrait lock stand in the way, which makes the Apple work smaller than the device's novelty suggests. Android is the reverse. URnetwork's compliance exposure there is already behind it, because the app targets API 36 and declares no locks. But by Google's own baseline it fails on the gesture that defines the device: folding and unfolding. Play's separate ratings by device type show that failure to exactly the high-spending users foldables attract.

The strategic opening is a layout the VPN category has left unclaimed: connect and locations side by side. URnetwork already ships it on the Mac. Bringing it to iPad, the Duo and Android is mostly a matter of putting existing screens together rather than redesigning them, and it also moves the connect graphic off the crease. Flip cover screens, by contrast, reward work on the tile, the notification and a Samsung widget more than work on layouts. Three questions remain open: the Duo's point sizes and Split View size classes, whether the inner display scales portrait-only apps, and whether Play's badge affects rankings. Their answers affect polish and testing, not the order of the work.

## Design direction agreed after this research (2026-10-28)

These decisions came from reviewing the split-screen mockups. Where they differ from the plan above, they replace it.

- **Connect at medium width and up shows statistics beside the connect canvas, not locations.**
  - The side pane is the connect drawer, always fully expanded. It holds:
    - client statistics: the Remote and Blocked charts and the transport mix;
    - local statistics and split rules;
    - Custom DNS;
    - "Block ads and trackers";
    - devices online.
  - The location stays a single row. Tapping it opens the picker as a dialog anchored in that pane, never across the fold.
  - This replaces the "locations beside connect" layout in item 10. Item 10's mechanics still apply: `SupportingPaneScaffold` on Android, `ArrangementView` on iOS 27.1, and keeping state above the layout switch.
- **Two panes at expanded width.** On an unfolded landscape screen (840 dp and up), a navigation rail, the statistics pane and the connect pane split at the hinge. Without a hinge, the split is 40/60.
- **A stacked split at medium width.** Unfolded portrait (600–839 dp) puts the canvas above, and compact statistics and Disconnect below.
  - Half-folded, the same split lands on the fold, so tabletop (item 17) needs no layout of its own.
- **Account and Leaderboard get list-detail splits.** This widens item 18 to both apps and adds Leaderboard.
  - Account keeps its list on the left and opens the chosen screen on the right.
  - Leaderboard keeps the ranking with its Data and Points tabs on the left, with "Your network" on the right: rank, data provided, points, longest streak, and the leaderboard visibility toggle.
- **Compact width is unchanged.** Folded phones and Split View beside another app keep today's phone layouts, and nothing is lost when the divider moves.
- **Samsung cover screen (item 16): one widget merging Dashboard, Globe and Contracts. Option A, accepted 2026-10-28.**
  - **Placement.** The provider globe fills the cover's camera corner, so the cameras only ever cover decoration.
  - **On top.** The location, status or the slow internet pill, and the toggle.
  - **Down the right.** Three tiles: Balance (the remaining balance and its bar), Traffic today (with a sparkline), and Contracts (the open count and the contract circles, the Contracts widget's design identity: the send stack → in green and the receive stack ← in pink, one circle per contract, drawn by `ContractStackRenderer`).
  - **States.**
    - Disconnected: the globe dims, and traffic and contracts read "—".
    - Locked: tapping the toggle asks the user to unlock, then connects without opening the app.
  - **Where it is offered.** On every Android device whose launcher can fit it, as a separate "super large" home screen widget. Its minimum of 352 × 339 dp (about 4 × 4 cells) decides that: a launcher that can't fit it simply doesn't list it. On Samsung Flips it also appears on the cover screen.
  - **Size.** It grows on tablets and unfolded phones, and lays itself out for the size it gets.
  - **Declaration.** One Glance receiver with the home screen and keyguard categories, the 352 × 339 dp minimum and Samsung's `sub_screen` meta-data. If Samsung's cover needs a keyguard-only widget, it becomes two receivers sharing one layout.
  - **The three existing widgets stay as they are.**
- **The mockups.** They are local HTML pages rendered to PNG: "Split screen and foldable layouts" and "One cover screen widget".

## As built (2026-10-28, uncommitted)

### Apple app

- **Rules.** `Shared/Extensions/SplitLayout.swift` holds the layout rules, with 18 tests in `SplitLayoutTests`. Layout reads the size class and measured sizes. `TabletLayout.isTablet`, the login's device-orientation tracking and both iPhone portrait locks are gone.
- **Connect.**
  - Compact width keeps the drawer, capped by the window and by a tabletop fold. The canvas shrinks to clear it.
